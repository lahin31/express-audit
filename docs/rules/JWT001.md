# JWT001 — Hardcoded JWT Secret

| Property   | Value            |
|------------|------------------|
| **ID**     | JWT001           |
| **Severity** | 🔴 Critical    |
| **Category** | Authentication |
| **Detector** | AST            |

## Description

A JWT secret key is hardcoded as a string literal in the source code instead of being read from an environment variable or a secrets manager.

## Why It Matters

Anyone who can read the source code — including contributors, contractors, or attackers who gain access to the repository — can extract the secret and forge arbitrary JWT tokens. This completely bypasses authentication. Historical git commits also retain the value forever even after it is changed.

## Vulnerable Example

```typescript
// ❌ Secret is visible in source code
const token = jwt.sign({ userId: user.id }, 'my-super-secret-123', {
  expiresIn: '1h',
});
```

## Secure Example

```typescript
// ✅ Secret is loaded from the environment
const token = jwt.sign({ userId: user.id }, process.env.JWT_SECRET!, {
  expiresIn: '15m',
});
```

Set `JWT_SECRET` in your environment or a `.env` file (never committed to git):

```
JWT_SECRET=a-long-random-string-from-a-csprng
```

Generate a cryptographically secure secret:

```bash
node -e "console.log(require('crypto').randomBytes(64).toString('hex'))"
```

## Remediation

1. Remove the hardcoded secret from source code immediately.
2. Rotate the secret (all existing tokens become invalid — this is the safest approach).
3. Store the new secret in your platform's secret manager (AWS Secrets Manager, HashiCorp Vault, Doppler, etc.) or as an environment variable.
4. Update deployment configuration to inject `JWT_SECRET` at runtime.
5. Add a pre-commit hook or CI check to prevent secrets from being committed again.
